# Independent review: cluster browse delegation and snapshot cancellation

Reviewed root integration `ce21d59` (browse routing) with `72b86ea` (lease-aware migration reads), `f2482cd` (synchronous Git descendant cleanup), and the cluster follow-up `7ec8fff` (stale delegated storage-generation rejection). The latter is on the cluster executor branch and was not yet integrated at the time of review.

## Scope and static findings

- Audited `src/sharding/transport.rs`, `src/browse.rs`, the browse handlers, object-format handlers, and ref transactions for source authorization, destination authorization, nonce consumption, endpoint/method/path binding, route epoch/fencing checks, and generation/watermark checks.
- The source checks the user token and repository role before routing. The destination independently revalidates the one-use signed envelope, authority incarnation, user token and revocation, repository role, target node identity and lease, route epoch/fencing token, and replica watermark. The nonce insert is in the same transaction as the destination checks, so failed checks roll back; a successfully admitted envelope cannot replay or cross paths. The forwarder deliberately replaces the bearer credential with the signed delegation and forwards the idempotency key.
- The browse route layer’s accepted method/path cases match the registered browse routes. Write-like endpoints route to the primary; read-only requests use read selection. `POST object-format/negotiate` is initially classified for primary placement while preserving read role; its handler validates the operation and independently demands write authorization for write operations.
- Root integration has the correct PostgreSQL-first ordering in browse/object-format handlers: acquire shared PG lease, then the local snapshot guard. The isolated cluster branch at `a47d1d5` predates that correction; its order must not be restored during integration.
- The `authenticate_delegation` code at `ce21d59` had a concrete stale-generation gap: it checked replica watermarks against the signed generation and route requirements, but not the current repository generation. An ingress could sign just before a generation-only update, then the destination would accept the old envelope after that update. `7ec8fff` adds a current-generation check and a native regression that advances the generation through a Forge backend PATCH without changing the route epoch, then tests stale and fresh browse/Git delegations.
- One availability edge remains to clarify in `7ec8fff`: `ConfigureRouteInput` permits `required_generation` to exceed `repositories.storage_generation`, and route selection signs `max(repo_generation, required_generation)`. Exact equality to current repository generation at the target intentionally fails closed in this state. Either document/test that unavailable behavior, or validate configuration so a future required generation cannot be installed until the repository generation reaches it.
- In `72b86ea`, all native migration Git reads (source fsck/bundle/ref digest and target clone/fsck/ref digest) run under `Lease::guard`; the shared lease is acquired before the local gate. The integrated `Process::Drop` synchronously kills and waits for the entire process group before a canceled read releases its local gate. `sync_tree` and request-body writes operate on private staging; a lease check gates target publication.

## Status

Static review and the independent current integrated native workload found no target-authentication, nonce-replay, or route-epoch bypass in the audited browse delegation path. The stale-generation finding is fixed in `7ec8fff`; the future `required_generation` floor semantics are handled by `eb035cf`. Keep the stale-generation regression open until the parent-provided attested binary containing both commits passes it. Do not count the older `aaf3638` binary as evidence for those two follow-ups.
