# Luna Max final integration review — 2026-11-09

This is a source-only review of the current authorized Push and metadata accepted-subset paths. I did not run Cargo, Git/native verification, PostgreSQL, services, or fixtures, so this is not a build or runtime qualification.

## Outcome

I found no remaining blocking source defect in the reviewed publication-decision, authorized pack, or metadata facade paths. The latest quota reservation changes address the liveness gap: an admitted metadata operation can finish after the counters reach their ceiling, and a new install refuses atomically when its required reservation cannot fit.

`CommitRefsRequest::validate` runs before `PgRefStore.begin` and checks both worst-case terminal shapes against the existing 64 KiB registry limit (`src/ref_store/core/command.rs:126-145`; `src/ref_store/core/terminal.rs:265-299`). A fresh metadata install charges its decision delta and reserves two 65,536-byte terminal/event bodies plus conservative bytes for every possible ref-row write before inserting the decision (`src/ref_store/core/publication_decision/metadata_install.rs:102-116`; `src/ref_store/core/publication_decision/usage.rs:198-223`). That charge is in the caller's transaction. Exact OPEN replay returns before the charge (`metadata_install.rs:63-99`), while final consume and the metadata ref/terminal/event writes do not charge again (`src/ref_store/core/authorized_metadata.rs:121-160`; `src/ref_store/core/metadata_subset.rs:218-294`). Thus quota refusal rolls back the pending operation and decision, and a committed reservation remains available to close the operation without refund or a second quota failure. The new real-PG quota case checks both properties (`tests/decision_subset_support/cases_d.rs:112-180`).

Installed-decision cancellation likewise has bounded headroom: `delta_for` includes a fixed 2,048-byte allowance (`src/ref_store/core/publication_decision/usage.rs:46-67`), greater than the maximum cancellation tombstone charge of 1,414 bytes (`usage.rs:29-30,71-76`; `contract.rs:32-34`), and cancellation skips a second charge when it binds a tombstone to an installed decision (`src/ref_store/core/publication_decision/cancel.rs:198-209`). Cancel-before-install charges the actual tombstone once. The allowance is currently implicit in the fixed padding; naming/documenting that component as the cancellation reserve would make this invariant easier to maintain, but I found no quota blocker in the current arithmetic.

The shared lock helper keeps tenant usage before repository usage and then the gate before protocol row (`src/ref_store/core/publication_decision/sql_locks.rs:1-18,205-245`); the final checks reread the real authorization, policy, captured refs, dependencies and fresh DB clock before consume (`publication_decision/metadata_check.rs:21-125`; `publication_decision/consume.rs:33-185`). Metadata issuer/actor equality is rejected before operation registration or replay (`src/ref_store/core/authorized_metadata.rs:48-61`), and rejected metadata decisions, terminal receipts, ref effects and events are handled in the same transaction (`authorized_metadata.rs:121-160`). Exact historical replay remains before the fresh-write fence in the legacy paths (`src/ref_store/core/pg.rs:308-359`; `src/ref_store/core/pack_commit/pg_commit.rs:49-67,195-245`). The public pack path's opaque verified proof/facts binding and selected-plan recheck were also reviewed; Merge remains explicitly fail-closed as unsupported for this Push-only batch.

The public cancellation and error cleanup paths use bounded rollback helpers, and `commit_bounded` bounds cleanup when the deadline expires before COMMIT; once COMMIT is sent, timeout/error remains `CommitUnknown` (`src/ref_store/core/authorized_metadata.rs:225-226`; `src/ref_store/core/pack_commit/authorized/mod.rs:231-239`; `src/ref_store/tx.rs:71-90`).

No source issue remains for this review pass. Build, migration application, and real-service behavior remain unqualified here because those checks are owned by Root.

## INSERT binding follow-up

The production failure identified in the native run was a real metadata INSERT binding defect: `authz_digest` had been bound to the metadata `facts_text`. The current source fixes it. `metadata_install.rs` now derives `authz_text` from `digests.authz_digest` and binds it as parameter 25 (`metadata_install.rs:126-153,156-190`), matching the 34-column order in its INSERT (`:193-202`). The source value is the live `authority.authz_digest` (`metadata_install.rs:120-132`), built from the actual token, repository lifecycle, effective role and ContentsWrite `AuthzFacts`, combined with the matching live `token_repository_scopes` rows (`metadata.rs:157-172,182-246`). The separate `facts_text` remains at parameter 24, as required by `facts_digest`.

I also mapped the pack INSERT independently. It has 38 columns, 38 parameters and placeholders `$1` through `$38` in matching order (`publication_decision/install.rs:235-286,287-298`); parameter 25 is `authz_digest`. That value comes from `DecisionDigests::compute(..., authority.authz_digest(), ...)` (`install.rs:135-147`), where `LiveAuthority::authz_digest` hashes the live `AuthzFacts` (`auth_deps.rs:65-85`). I found no analogous pack binding mismatch. The source now reflects the metadata fix; I did not rerun any build or test command.
