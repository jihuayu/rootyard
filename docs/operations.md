# Operations and recovery

## Deployment boundary

Run on Linux as a dedicated unprivileged identity with exclusive write access to the data directory (`ROOTYARD_DATA_DIR`, or `ROOTYARD_SCRATCH_DIR` for candidate `serve-blob`). Keep the binary and configuration outside those directories. Do not permit tenants to edit bare repositories, hooks, configuration or parent directories. Never share the volume among serving nodes or run manual Git maintenance while writes are active.

Terminate HTTPS at a trusted reverse proxy before exposing the service beyond `localhost` / `127.0.0.1`. Configure the proxy to strip untrusted forwarding headers and set `X-Forwarded-Proto: https` on TLS-terminated requests so browser sessions receive `Secure` cookies and pass same-origin checks (`Host` vs `Origin`); non-loopback HTTP sign-in is rejected with `403`. Note that pre-DB authentication admission (`ROOTYARD_AUTH_ADMISSION_*`) keys strictly on the TCP peer socket (`ConnectInfo`) and intentionally ignores `X-Forwarded-For` / `Forwarded`. Do not log `Authorization` headers, session cookies or token-bearing URLs. Set upstream request/time limits consistently with Rootyard; a proxy disconnect can leave a push outcome unknown.

For PostgreSQL outside local development, use a private network with `sslmode=require` plus `ROOTYARD_PG_CA_PEM` (and optional `ROOTYARD_PG_CLIENT_CERT_PEM` + `ROOTYARD_PG_CLIENT_KEY_PEM` for client mTLS), which enables Rustls certificate and hostname validation across runtime pools, hooks and backup/restore connections. `sslmode=require` without `ROOTYARD_PG_CA_PEM` fails closed, and setting `ROOTYARD_PG_CA_PEM` with any weaker `sslmode` is rejected to prevent TLS downgrade.

The database and volume (plus configured remote object storage for LFS, Pando or `serve-blob`) together comprise the service state. Protect database credentials, object-store credentials and backups; token digests are not plaintext credentials but the database remains sensitive. CLI token issuance (`create-user`, `create-token`) is an administrative capability requiring database access.

## Resource limits and destructive-deletion defaults

Request/output limits count streamed bytes; oversized Git operations can fail after transport has begun. Git subprocess deadlines run independently of a slow client reading responses. Normal cancellation uses TERM followed by a one-second grace period and KILL; cleanup keeps process-group identity until the leader is reaped. Encoded gzip/x-gzip requests have both wire-byte and decoded-byte caps. These deadlines, address-space limits and process concurrency are defensive bounds, not a workload sizing model. Address space is not identical to resident memory. Reserve capacity for the Rust server, database, filesystem cache and concurrent processes.

Run containers with an init reaper (`docker run --init` or Compose `init: true`, already configured here). Rootyard waits for its direct Git child; orphaned Git grandchildren stopped during group cleanup must be reaped by the container's init. Running the image as PID 1 without an init is not supported. See [Docker's init option](https://docs.docker.com/reference/cli/docker/container/run/#specify-an-init-process).

The repository byte threshold (`ROOTYARD_MAX_REPO_BYTES`) is an admission check, not a hard atomic storage quota (`#83`). Concurrent receive operations, quarantine packs and temporary files need headroom. Use filesystem quotas, disk alerts and an appropriate container/system service memory limit for stronger deployment-level controls. Never infer a safe arbitrary-concurrency load from defaults.

Destructive background and remote object deletion stay disabled unless explicitly enabled where supported: `ROOTYARD_STORAGE_MAINTENANCE` defaults to `false`, `ROOTYARD_PANDO_REMOTE_DELETE` defaults to off, `ROOTYARD_WORKSPACE_UNSAFE_REMOTE_DELETE` defaults to `false`, and OpenDAL `BlobStore::delete` is unconditionally `DeleteDisabled`. Never point an out-of-band PostgreSQL PITR or basebackup clone at a shared deletable S3/Blob bucket (`#77`).

Failures after HTTP headers have been sent cannot change the status code: a response that began with `200` can end as a failed/truncated stream. The Git client must consume and validate the complete protocol result, not treat the status alone as success. A push rejected by timeout, stream cap or disconnected transport may have reached a ref update already. Reconnect, inspect the actual remote refs and run a normal fetch before deciding whether to retry. Native Git's result is authoritative.

## Startup and interrupted provisioning

Use the same database and data volume when restarting. Only one serving process may own the directory. Startup prepares or verifies `schema 147` (`ROOTYARD_SCHEMA_MODE=auto|external`), re-verifies that no `.rootyard-restoring` guard is present, and reconciles pending provisioning records with on-disk repositories, at most 64 due records per scan with persisted attempt counts and 30-second retry backoff. Recovery can rebuild an unpublished `.init` tree under the exclusive volume lock, including stale staging `config.lock` files; it is not a comprehensive repair tool for missing ready repositories, corrupted objects or arbitrary manual changes.

If startup reports a lock conflict, find and stop the existing owner normally; do not bypass locking. Git children inherit the volume lock, so a receiver surviving an abrupt parent termination can intentionally prevent another server from starting until the child exits. If storage is missing or corrupt, stop writes and investigate the database/volume pair. Do not delete database rows or initialize an empty replacement repository over existing state. Preserve evidence and restore a matched backup when necessary.

A force-killed Git operation can leave `.lock` files in a **ready** repository. These are never automatically deleted. Before any manual repair: stop Rootyard and every writer/maintenance process, take a coordinated database-and-volume backup, inspect the repository and process state, run `git fsck --full`, and establish that the specific lock is stale rather than owned by an active operation. Remove only the individually verified stale lock as an explicit operator repair, then recheck refs and integrity before reopening writes. Do not use a blanket `find ... -delete` cleanup.

Revoking an API token immediately invalidates any child `rootyard_session` browser sessions derived from it and blocks subsequent authentication or late Git ref-publication checks (which lock the token `FOR SHARE` before ref CAS); it cannot retract bytes already delivered to a client.

## Coordinated offline backup and isolated restore

The maintenance commands are `rootyard backup PATH --offline`, `rootyard backup-verify PATH` and `rootyard restore PATH --isolated --trust-backup [<LEGACY_FLAG>]`. Read [the full backup/restore contract](backup-restore.md) before using them. Current archives use `schema 147`: `format 21` for legacy GitFS/Pando/LFS deployments (`0` `pg_refstore` serving repositories, no OpenDAL Blob bytes) and `format 22` when any `pg_refstore` serving repository exists (validated RefStore artifact ledger + same-backend OpenDAL Blob `.pack`/`.idx` closure). Backup refuses a live volume owner or active `serve-blob` lifecycle barrier, freezes all supported PostgreSQL tables under `REPEATABLE READ`, and captures a matched database dump, volume tree, and applicable Pando or OpenDAL Blob closure. Restore requires a fresh dedicated PostgreSQL 17 database, a nonexistent data directory, and the exact producing binary (or one explicit legacy upgrade flag: `--allow-legacy-schema007`, or `--allow-legacy-schema130` through `--allow-legacy-schema143`), verifies hashes and native integrity, fences old execution/session credentials, preserves unknown evidence, and never starts a service or switches traffic.

This is not an online or lossless-backup promise. Restore failures leave private partial material and may have an uncertain SQL commit; persistent filesystem and database restore guards block startup pending operator review. Keep standalone `worker` / `worker-once` processes stopped until restore completes ([cross-process-workers.md](cross-process-workers.md)). Do not overwrite targets, mix backup generations or remove guards to bypass an incident. See [backup-restore.md](backup-restore.md) and [historical integrated verification](integration-verification.md) for tested recovery boundaries.

## Durable operation recovery (introduced in historical migration 002, active through `schema 147`)

Read [ADR 002](reliability.md) and [manual-recovery.md](manual-recovery.md) before performing incident recovery. Originally introduced in migration `002` (now part of `SCHEMA_VERSIONS` through `147`), GitFS operation recovery keeps native Git authoritative. The data volume must allow execution of the private `.runner` hook binary; startup performs a harmless execution probe and requests verify actual executable access. A `noexec` data volume fails closed. Linux procfs must expose every service-UID process for safe descendant cleanup.

Keep the entire data directory, not only `repos/`, in coordinated offline backups. Do not remove journals or sequence counters, manually clear an unknown operation, or lower a generation. An unknown result may mean Git changed refs even if the client received an error. Repository operation summaries are available at `/api/repos/{owner}/{name}/operations` (subject to repository RBAC and PAT scope). PostgreSQL holds full bounded evidence. `rootyard worker-once` drains one bounded batch for each built-in consumer; it does not resolve unknown writes.
