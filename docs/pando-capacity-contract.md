# Blob-Only Pando Multi-Layer Capacity Contract (`#177`)

This document defines the end-to-end capacity contract for the standalone Blob-only Pando profile (`PostgreSQL RefStore + OpenDAL BlobStore + stock Git`) and documents the bounded streaming-growth, admission, and retention-ledger mechanisms implemented under [`src/blob_store/capacity_contract.rs`](../src/blob_store/capacity_contract.rs).

Every figure below is tagged with its exact verification status:
- **CurrentCodeFact**: literal constant enforced in existing `origin/main` code (`src/config.rs`, `src/blob_git_gateway/`, `src/blob_store/`, `src/ref_store/core/`).
- **EnforcedBoundedEngine**: policy enforced by [`limits.rs`](../src/blob_store/capacity_contract/limits.rs), [`admission.rs`](../src/blob_store/capacity_contract/admission.rs), [`streaming_growth.rs`](../src/blob_store/capacity_contract/streaming_growth.rs), and [`ledger_retention.rs`](../src/blob_store/capacity_contract/ledger_retention.rs).
- **MeasuredBenchmarkBaseline**: reproducible outputs generated by [`scripts/eval_pando_capacity.py`](../scripts/eval_pando_capacity.py); performance targets are calibrated by `#164` real mixed-workload measurements rather than preset production SLAs.

### Why Constants Cannot Simply Be Bumped
1. **Gateway `128 MiB` != Verifier `64 MiB`**: A push accepted at the gateway wire spooler (`128 MiB`) still fails closed if unpacked objects exceed `16,384` objects, `64 MiB` pack+idx per verification window, or `160 MiB` materialized workspace (`VERIFIER_VIEW_MAX_LOGICAL_BYTES`).
2. **Metadata `8 MiB` != Repository Content Size**: `REPO_MAX_LOGICAL_BYTES = 8 MiB` counts PostgreSQL ledger rows and JSON receipt bodies (`256 B` row overhead + bounded ACK/terminal bodies). Multi-gigabyte repositories live in `BlobStore` (`1 TiB` per object ceiling).
3. **`MAX_ACTIVE_MEMBERSHIPS = 16` & `VERIFIER_GIT_NOFILE = 64`**: Each active pack+idx pair consumes `2` FDs during `git` verification plus `~24` Git process FDs (`16 * 2 + 24 = 56 <= 64`). Bumping `16` to `64` without compaction would hit `EMFILE` (`64` NOFILE), exceed `160 MiB` scratch disk, and cause `O(N)` read/write amplification.

## 2. Streaming Growth, No-New-Pack Updates & No-Delete Compaction

[`StreamingGrowthEngine`](../src/blob_store/capacity_contract/streaming_growth.rs) resolves the `> 16` pack-count and `160 MiB` workspace bottlenecks while keeping all closure, authorization, and retention invariants intact:

1. **No-New-Pack Pushes (`new_pack_paths.is_empty()`)**: Fast-forward moves to existing commits, branch/tag creations over existing objects, and ref deletions add **0** packs (`cumulative_packs_added` unchanged, `no_new_pack_pushes += 1`), while still verifying `cat-file` object presence and `git fsck --connectivity-only` against the active frontier.
2. **Idempotent Retries & Bounded Cancellation**: Replays of an acknowledged `(operation_id, request_digest)` return the persisted `PushOutcome` (`replayed: true`) without duplicate pack writes; digest reuse conflicts fail closed (`DigestConflict`). Late `cancel_operation` on an already-acknowledged operation rejects (`InvalidInput`) so a replay cannot flip to `OperationCancelled`; cancellation tombstones for unacknowledged operations never commit refs or packs, and both replay and cancellation maps are capped at `max_resident_replay_ops` (`4096`).
3. **Real Unpacked Inspection, Process Limits & Scratch Reclaim**: [`git_ops.rs`](../src/blob_store/capacity_contract/git_ops.rs) and [`git_views.rs`](../src/blob_store/capacity_contract/git_views.rs) stream pack hashing in `64 KiB` chunks, pipe `.pack` files straight to `git index-pack --stdin` via `Stdio::from(File)`, unlink `incoming/` files after indexing (`AdmissionPermit::shrink_workspace`), inspect actual unpacked objects via `git cat-file --batch-all-objects --batch-check=%(objectsize)` against `max_single_object_bytes` and summed `view_max_logical_bytes` (never trusting caller-declared `IncrementalPushRequest::max_single_object_bytes` alone), enforce Unix `pre_exec` `setrlimit` (`setpgid`, `RLIMIT_AS=512 MiB` with `-c pack.threads=1` on `repack`, `RLIMIT_CPU=20 s`, `RLIMIT_FSIZE=128 MiB`, `RLIMIT_NOFILE=64`, `RLIMIT_CORE=0`), and bound stdout/stderr pipes at `VERIFIER_PIPE_BYTES` (`2 MiB`).
4. **No-Delete Compaction & `closure_revision` Fencing (coordinated with `#162` & `#122`)**: When active serving packs approach `compact_trigger_packs = 12`, a `CompactionMaintenance` task (capped at `<= 50%` concurrency) snapshots `closure_revision`, `active_packs`, `acked_refs`, and `pinned_commits` inside a private `0o700` `DisposableViewRoot` subdir. Client refs are barred from the reserved `refs/pando-pins` / `refs/pando-pins/` namespace (`validate_mutations` & `validate_client_refs`), while pinned OIDs are injected via separate `pinned_oids`. After `git repack -a -d`, `pre_oids == post_oids`, and `git fsck --full --strict`, commit validates both `target_ids.is_subset(&active_ids)` AND unchanged `closure_revision` (failing closed with `CompactionConflict` if a concurrent push, no-new-pack ref mutation, or pin change happened mid-compaction). Aborted/rejected Blob uploads are tracked in `failed_attempt_count`, `failed_attempt_blob_bytes`, `total_blob_put_bytes`, and bounded `failed_attempt_pack_locators()` (capped together with `retained_old_packs` by `max_retained_pack_records = 1024`). Old packs remain physically retained in `BlobStore` (`delete_during_compaction_enabled = false`; physical GC stays isolated under `#122`, related `#163` / `#83`).

## 3. Fail-Closed Admission & Historical Ledger Retention

- **Bounded Admission ([`admission.rs`](../src/blob_store/capacity_contract/admission.rs))**: Enforces authorization (`Unauthorized`), scope validation, single-object size (`OversizedObject`), pack bytes (`PackBytesExceeded`), object count (`TooManyObjects`), frontier pack limit (`PackCountLimitReached`), workspace (`WorkspaceBudgetExceeded`), memory (`MemoryBudgetExceeded`), FD budget (`FdBudgetExceeded`), disk headroom (`DiskHeadroomExhausted`), bounded waiter queue (`QueueFull`), and deadline expiry (`DeadlineExceeded`) with RAII permit/queue cleanup. No rejection ever emits a false-OK.
- **Protected vs. Released Retention Ledger ([`ledger_retention.rs`](../src/blob_store/capacity_contract/ledger_retention.rs))**: Every `Membership`, `Registration`, and `Receipt` row starts as `ActiveProtected`. Compaction moves replaced entries out of the active frontier while keeping every `Pin`, `RetentionRoot`, and `BackupManifest` hold intact (`CompactedProtected`). Calling `attempt_delete_entry` fails closed (`ProtectedByHold` or `CompactionDoesNotAuthorizeDelete`). Resident ledger entries stay bounded by `repo_max_resident_entries` (`4096`), failing closed until released entries (`ReleasedEligibleForArchive`) are explicitly checkpoint-archived (`archive_released_entries`), draining cold records into cumulative counters (`archived_memberships`, `archived_registrations`, `archived_receipts`, `cold_logical_bytes`) without deleting protected history.

## 4. Verification Scope, Reproducible Evaluation & `#164` Policy

- **Verified In-Process / OS-Child Scope vs. Deferred Server Acceptance (`#177` stays `OPEN`)**: This module proves contract validation, OpenDAL S3 + `DisposableViewRoot` + stock-Git child enforcement (`RLIMIT_*`, `pipe_bytes`, `cat-file` unpacked object checks), `> 16` pack growth, `closure_revision` compaction fencing, failed-upload byte accounting, and ledger retention in-process and under [`tests/pando_capacity_contract.rs`](../tests/pando_capacity_contract.rs). Full end-to-end Smart-HTTP gateway + live PostgreSQL RefStore multi-worker deployment capacity acceptance remains **open on `#177`** for separate server wiring and `#164` calibration.
- **Evaluator (`MeasuredBenchmarkBaseline`)**: [`scripts/eval_pando_capacity.py`](../scripts/eval_pando_capacity.py) measures standalone stock `git` (`sha1` & `sha256`) multi-pack growth across `8`, `16`, `24`, and `32` packs with interleaved no-new-pack ref updates, bounded queue workers, no-delete compaction, and optional [`native_build_receipt.py::validate_receipt`](../scripts/native_build_receipt.py) verification. It reports throughput (`ops/s`), latency (`P50/P95/P99/max`), child/process `RSS`, peak scratch disk bytes, separated Blob PUT/GET/active-serving/retained-old-pack bytes, and queue wait; production capacity targets remain bound to `#164` empirical baselines rather than preset SLAs.
